# Workflow Audit

This page documents how the four pillars of a tidy GitHub workflow fit together: **branches**, **pull requests**, **issues**, and **close-out**.

## How It All Fits Together

1. **Branch** — Feature work starts on a dedicated branch (e.g. `feature/audit-notes`) off the default branch (`main`). This keeps the default branch stable and readable.
2. **Commit** — Small, focused commits with clear messages ("Add audit documentation") make review and history easy to follow.
3. **Pull Request** — A PR (` feature/audit-notes` → `main`) is the formal request to merge changed work. It is where conversation, review, and CI checks happen before anything lands on `main`.
4. **Issue** — A tracked item (e.g. "Demo: workflow checklist") captures the *why* and the acceptance criteria. Sub-issues break it into smaller follow-ups that stay attached to the parent until it is done.
5. **Review** — A reviewer reads the diff, leaves line-level comments, and either approves, requests changes, or comments.
6. **Close-out** — Once the PR is merged and the checklist issue is marked **Completed**, the work is formally closed. Open follow-up issues stay open until their own due date.
